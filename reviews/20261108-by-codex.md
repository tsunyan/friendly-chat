# friendly-chat レビュー

レビュー日: 2026-11-08  
対象: `README.md`、`skills/friendly-chat/SKILL.md`  
観点: 主に職場の日本語チャットで、表現、理解、判断、返信、作業の中断などによる相手の負荷を減らせるか。

本文を読んだ設計上のレビューであり、実際の利用者を対象に負荷軽減の効果を測定したものではない。スキル名の正規表現については、後述する文字列との一致を確認した。

## 総評

趣旨にはよく合っている。用件を先に出す、リンクに要点を添える、担当を明示する、決定を残す、といった方針は特に有用。「やさしい表現」にとどまらず、読む・判断する・返す・探す手間を扱えている点もよい。

一方で、「読み手の負荷を減らす」という原則より、個別の書き方のルールが強くなっている箇所がある。形式をそろえるために意味を変えたり、情報や確認作業を増やしたりしないことを、適用時の優先原則にしたい。

改訂するなら、意味を変える例文の修正、断定的なルールの条件化、返答を強制しない選択肢の整備を優先する。

## 内容のレビュー

### 1. 最優先: 例文でも意味や条件を変えない

「範囲と前提」には、意味、事実、条件、数値、期限を変えないという適切な原則がある。ただし、一部の例文や置換ルールが矛盾している。

- 「明日まで」→「明日の12時まで」: 元にない時刻を追加し、期限を狭めている。
- 「基本的に毎回落ちます」→「毎回落ちます」: 例外の可能性を消している。
- 「〜したいと思います」→「〜します」: 意向や提案を、確定した約束に変える場合がある。

相手が誤った前提で動けば、読みやすさ以上の負担になる。例文でも条件を維持し、情報の補足は文体の修正と分けて提案する。

例:

> 明日までに、レビューをお願いできますか？

時刻が必要なら、下書きとは別に「締め切り時刻が決まっていれば補ってください」と伝える。「したいと思います」は、単なる冗長表現なのか、未確定の意向なのかを確認してから直す。

### 2. 短く答えることより、条件を取り違えさせないことを優先する

「はい/いいえ」で先に答える節のマージ承認の例は、条件を後ろに置いている。

> はい、大丈夫です。ただ、CIが通っているかは確認してください。

冒頭だけ読むと承認に見える。条件が成立した場合にだけ許可できるなら、次の形がよい。

> CIが通っていれば、マージして大丈夫です。

また、「事実は言い切る」の例では、TTLを変更して症状が消えたことから、原因が確定するように書かれている。症状が消えることと、根本原因が確定することは同じではない。

> stagingではTTLを0にすると再現しなくなりました。TTLの設定が関係している可能性がありますが、原因はまだ確定していません。

観測した事実、推測、未確認事項を区別する。読みやすさのために、確信の度合いを上げない。

### 3. 表現の禁止より、「読み手が迷うか」で判断する

指示対象が明確なスレッドでの「この案」、1対1のDMでの「私」、専門家同士の略語まで置き換えると、かえって長く不自然になる場合がある。

漢字の開き方、空行の頻度、太字の数も、一律の合否判定にしないほうがよい。表示上の行数は、画面幅や端末にも左右される。

本文には場面への配慮があるが、「仕上げのチェック」では「指示語・略語がない」「ひらく語が残っていない」という形式的な判定に戻っている。次のように目的で判定したい。

- 指示語の対象や、担当者を取り違えないか。
- 想定する読み手が理解できない略語が残っていないか。
- 漢字やひらがなが続きすぎず、語の区切りを読み取れるか。
- 意味のまとまりごとに区切られ、必要な箇所を見つけられるか。

### 4. 返答を簡単にする工夫が、同意や監視の負担にならないようにする

はい／いいえの質問は、前提が合っていれば答えやすい。しかし前提が違う場合には、訂正の説明が必要になる。選択式の質問は、情報不足、別案、判断できないという回答もできる形にしたい。

「異論がなければ進める」は、相手に期限までの確認を事実上求める。取り消しにくい決定や相手の権限に属する決定を除外している点はよいが、次の条件も補いたい。

- 書き手の裁量で進められることか、事前に合意した運用である。
- 相手が読んでいない可能性を考慮し、無回答を承認とみなさない。
- 確認や承認が必要な依頼では、回答がない場合の相談先や保留方針を決める。

リアクションも、返信不要の共有に毎回求めれば新しい仕事になる。「文章より返信が軽い」と「返信そのものが不要」は区別する。

### 5. 気持ちへの配慮と、必要な情報の省略は分ける

「知ってました」という返し方を避けるのはよい。しかし「知っていたと示しても得はない」は強すぎる。既知の範囲を伝えることには、重複説明を止め、相談の論点を絞る意味がある。

> ありがとうございます。設定方法は確認済みで、今回は権限の部分を相談したいです。

お礼と論点整理を両立させるほうがよい。実際には新しく役立つ情報でなかった場合まで、「助かります」に置き換える必要はない。

依頼をやわらげる場合も、「〜だとうれしいです」で必須の作業を任意に見せないようにする。必要性と期限を明確にしたうえで、断る・延期する余地を具体的に示す。

### 6. 優先順位と要約の整合性を調整する

「上の節ほど効果が大きい」という固定順位には、本文中で裏付けが示されていない。場面によっても順序は変わる。ミスの指摘では心理的負担、障害報告では正確さと緊急性が先になる場合がある。「通常の確認順」と位置づけ、場面ごとの調整を認めたい。

READMEと本文、原則と例文の間にも、次の不整合がある。

- READMEの「間違いの指摘はDMで伝える」は、本文の「ほかの人が知る必要がなければ」という重要な条件を落としている。
- READMEの「自分・こちらではなく、人の名前で書く」は、本文の「担当が複数いる文や、転送されそうな文」という条件を落としている。
- 「行動してほしい人だけにメンションする」という原則に対して、例文では共有のみの佐藤さんにもメンションしている。

READMEでも例外条件を残し、例文を原則に合わせる。

## 追加・強化したい手法10個

以下はすべてのメッセージに追加する必須項目ではない。必要な場面にだけ使う。例文の期限、権限、対応方針は、実際に決まっている場合にだけ書く。

### 1. 依頼の範囲と、終わりの条件を示す

「確認お願いします」だけでは、どこまで見ればよいかわからない。既存の「見てほしい場所を示す」に加え、完了と判断できる条件を書く。

> 金額と対象人数の2点を確認してください。文言の校正は今回の対象外です。

作業を広げすぎる負担と、確認漏れへの不安を減らす。「すぐ終わるので」と所要時間を軽く見積もらないことも大切。

### 2. 返答の期限と、作業完了の期限を分ける

> 対応可能かを11/12までに教えてください。作業の完了希望は11/15です。

予定に入れられるかの確認と、実作業を分けることで、受け手が調整しやすくなる。両方が必要な依頼だけに使う。

### 3. 断る・延期する場合の具体的な進め方を示す

「難しければ言ってください」だけでは、断った後の影響が気になることがある。

> 今週の対応が難しければ、来週に変更できます。難しい旨だけ返信してください。

やわらかい語尾に加えて、実際に選べる余地を用意する。書き手に認められた調整範囲を超える代案は作らない。

### 4. 選択肢に「どちらでもない」「判断できない」の余地を残す

> A案を推しています。B案、別案、情報不足でも、その旨を教えてください。

選択式にすることで、無理に同意させたり、誤った前提に沿って答えさせたりするのを防ぐ。

### 5. 複数の質問では、優先順位と部分回答の可否を示す

> まず1だけわかれば着手できます。2と3は明日でも大丈夫です。

番号だけでなく回答順も示すと、全部そろうまで返信を保留する必要がなくなる。

### 6. 再確認の依頼では、前回からの変更点を先に書く

> 前回からの変更は納期と担当者の2点です。変更箇所は黄色で示しました。

受け手が資料全体を読み直し、差分を自力で探す手間を減らす。変更箇所だけの確認でよいかも明示する。色だけに頼らず、変更点を文字でも説明する。

### 7. すぐに答えられないときは、次に連絡する時点を伝える

> 確認しています。11/12の15時に、未解決でも状況を共有します。

「確認します」だけで止めず、相手がいつまで待てばよいかをわかるようにする。解決時刻を無理に約束する必要はない。

### 8. 完了・解決・依頼の取り下げを知らせる

> 別の方法で解決したため、この調査依頼は取り下げます。追加対応は不要です。

決定事項のまとめに加えて、相手が覚えておく必要のなくなった用件を閉じる。重複作業や、気にし続ける負担を減らせる。

### 9. 添付先を、受け手が実際に読める状態にする

要点を添えるだけでなく、閲覧権限、対象の版、スマートフォンでも読めるかを確認する。画像の重要な数値やエラー文は本文にも書く。

> 対象は11/12更新版の3ページ目です。確認してほしい金額は税込12万円です。

アクセス申請や画像の読み取りで往復するのを防ぐ。

### 10. 送信前に「受け手が次に何をするか」を一度たどる

禁止語チェックに加えて、「何を開くか」「何を判断するか」「何と返信するか」「何を覚えておくか」を確認する。

「確認お願いします」から確認対象を推測する必要があれば補う。反対に、短い返事で十分なら説明を足さない。ルールを増やして文面を重くするのを防ぐ、最終判断として使う。

## 追記されたスキル名の指定パターンのレビュー

対象は、SKILL.mdのdescriptionに追加された次の文。

> /フレ(ンド(リー)?)?チャ(ット)?|fr(iend(ly)?)?[ _\-]?ch(at?)?/ とスキル名を指定された場合に使う。

### 判定

正式名称だけでなく略称でも指定できるという意図はよい。パターンは主な略称に一致する。ただし、名前全体の照合か部分一致か、大文字・小文字の扱い、単なる言及と利用指定の区別を明確にしたい。

descriptionに正規表現らしい文字列を書くことと、その正規表現を実行してスキルを選択することは別である。今回の確認はパターン自体の一致結果であり、各エージェントでの実際の起動を検証したものではない。

### 確認した一致結果

外側のスラッシュを区切り記号とみなし、その内側をPowerShellの.NET正規表現で照合した。大文字・小文字を区別する、部分一致の条件。実際のエージェントがこの方式でdescriptionを処理するという意味ではない。

| 入力 | 一致 | 一致した部分 |
|---|---|---|
| フレチャ | する | フレチャ |
| フレンドリーチャット | する | フレンドリーチャット |
| frch | する | frch |
| friendly-chat | する | friendly-chat |
| friendly chat | する | friendly chat |
| friendly_chat | する | friendly_chat |
| Friendly-Chat | しない | — |
| FRCH | しない | — |
| friendly-chart | する | friendly-cha |
| friendly-challenge | する | friendly-cha |
| フレチャート | する | フレチャ |
| afrchive | する | frch |
| friendly　chat（全角スペース） | しない | — |

### 改善したい点

1. **名前としての指定と、部分一致を区別する。** `friendly-chart`などの別の語に含まれるだけでは使わない。正規表現をプログラムで使うなら、文中から取り出した名前全体への一致を確認する。ユーザーの依頼文全体にアンカーを付けると、「フレチャで直して」のような自然な依頼を拾えなくなるため、照合対象の単位も決める。
2. **大文字・小文字と区切り文字の扱いを決める。** 英語名の大小文字を区別しない方針が扱いやすい。全角スペースなども許容するなら、正規化するか、許容表記として明示する。
3. **`ch(at?)?`の意図を確認する。** これは`ch`、`cha`、`chat`を許容する。`cha`も略称として意図しているなら問題ない。`ch`と`chat`だけを許容したいなら`ch(at)?`になる。
4. **利用指定と、単なる言及・引用・レビューを分ける。** 「フレチャでこの返信を直して」は利用指定だが、「フレチャの説明をレビューして」はスキルそのもののレビュー依頼。今回のように正規表現を引用して確認する依頼も、文面推敲として適用する指示ではない。
5. **明示指定時にも対象範囲が変わらないかを明確にする。** 現在は「名前を指定されたら使う」と「メール等には使わない」が並んでいる。既存の対象範囲を維持するなら、「対象の日本語チャットの作成・推敲で」と条件を付ける。明示指定で対象外にも使わせたい意図なら、対象範囲側の説明も調整する。

### descriptionの修正文案

正規表現だけに依存せず、代表的な呼び方と利用意図を自然言語で示す案。

> 対象の日本語チャットの作成・推敲で、「friendly-chat」「friendly chat」「friendly_chat」「frch」「フレンドリーチャット」「フレチャ」などの正式名称や略称を使って、このスキルの利用を指定された場合にも使う。英語名の大文字・小文字は区別しない。名前への単なる言及、引用、スキル自体の説明・レビュー依頼は利用指定とみなさない。

既存の「スキル名が出ていなくても使う」という自然な依頼からの適用条件は残す。正規表現の表記も残したい場合は、前記のパターンに「スキル名全体として一致する呼称」「英字は大小文字を区別しない」「利用指定がある場合」という条件を添える。

修正文案は、明示指定でも既存の対象範囲を維持する前提。正式名称以外の表記をどこまで保証するかは、対応するエージェントで実際に試して判断する。
